Absolutely. Since you want **only two core features — Static QR and Dynamic QR**, the PRD should be deliberately focused. The sophistication should come from **quality, editing, analytics, reliability, security, and UX**, not from adding dozens of QR types.

# Product Requirements Document — Dynamic & Static QR Platform

**Working product name:** QR Platform
**Document version:** 1.0
**Product type:** Web SaaS
**Primary features:**

1. Static QR Generator
2. Dynamic QR Generator + Analytics

**Core principle:**

> **Static QR = generate once, works forever.**
> **Dynamic QR = edit anytime, track every scan.**

---

# 1. Executive Summary

The product is a web-based QR platform that allows users to create two kinds of QR codes:

### Static QR

The user's information is encoded directly into the QR code.

```text
User enters destination
        ↓
QR generated
        ↓
Information encoded directly
        ↓
Download / share
```

Once generated, the encoded information cannot be changed.

### Dynamic QR

The QR contains a platform-managed redirect URL.

```text
User enters destination
        ↓
Platform creates unique QR
        ↓
QR contains platform redirect
        ↓
User scans
        ↓
Platform records scan
        ↓
Platform resolves destination
        ↓
User redirected
```

The destination can subsequently be changed without reprinting the QR.

---

# 2. Product Vision

> **Make QR creation extremely simple while making dynamic QR codes measurable, editable, reliable, and secure.**

The product should not attempt to become:

* A website builder
* A marketing automation platform
* A CRM
* A payment platform
* A social media tool
* A huge QR-type marketplace

The product has one job:

> **Create QR codes and, for dynamic QR codes, give users control and useful analytics.**

---

# 3. Product Goals

## Primary goals

### G1 — Extremely simple QR creation

A first-time user should be able to create a QR in less than one minute.

### G2 — High-quality QR generation

Generated QR codes must be:

* Scan reliable
* High resolution
* Exportable
* Customizable
* Print friendly

### G3 — Reliable dynamic QR infrastructure

Dynamic QR links must:

* Resolve quickly
* Remain stable
* Support destination editing
* Handle high traffic
* Record scan events reliably

### G4 — Useful analytics

Users should understand:

* How many times the QR was scanned
* When it was scanned
* Approximate geographic distribution
* Device information
* Unique vs total scans
* Scan trends

### G5 — Complete edit history

Users should know:

* What changed
* When it changed
* Who changed it
* Previous value
* Current value

# 15. Dynamic QR Creation

User enters:

### QR Name

```text
Summer Sale Poster
```

### Destination

```text
https://example.com/summer-sale
```

Then:

**Create Dynamic QR**

System generates:

```text
https://qr.yourdomain.com/x8K29
```

That URL is encoded into the QR.

---

# 16. Dynamic QR URL Requirements

The generated identifier must be:

* Unique
* Non-sequential
* Unpredictable
* URL-safe
* Short enough for practical QR encoding

Example:

```text
qr.example.com/a8Kx92
```

Avoid:

```text
qr.example.com/12345
```

because predictable identifiers create unnecessary enumeration risk.

# 17. Dynamic QR Editing

### Destination URL

Before:

```text
https://example.com/offer
```

After:

```text
https://example.com/new-offer
```

The QR image remains unchanged.

# 18. Dynamic QR Lifecycle

Each dynamic QR has a state.

```text
ACTIVE
   │
   ├── EDIT
   │
   ├── PAUSE
   │
   ├── RESUME
   │
   └── ARCHIVE
```

### Active

Redirect works normally.

### Paused

QR displays a configurable fallback message or platform-managed inactive page.

### Archived

QR is no longer actively managed.

# 47. Dynamic Redirect Performance

When a user scans:

```text

 ↓

 ↓
```

Preferred architecture:

```text

             │
             ▼
```

# 52. Important Database Rule

Never overwrite important historical information.

Bad:

```text
qr.destination = new_url
```

with no history.

Better:

```text
qr_destinations

V1 → old URL
V2 → new URL
V3 → another URL
```

Current destination points to V3.

This enables auditability.

# 54. Dynamic Redirect Security

This is extremely important.

Because your infrastructure will effectively host:

```text
qr.yourdomain.com/*
```

you must prevent abuse.

Implement:

### URL validation

Accept:

```text
https://example.com
```

Reject:

```text
javascript:...
data:...
file:...
```

and other unsafe schemes.

### HTTPS preference

Warn or restrict HTTP destinations depending on product policy.

### Abuse detection

Monitor:

* suspicious domains
* phishing URLs
* malware indicators
* excessive QR creation
* unusual redirect activity

---

# 55. SSRF Protection

The backend must **not blindly fetch arbitrary user URLs**.

For example, if you implement URL metadata previews or destination verification, protect against:

```text
localhost
127.0.0.1
private IP ranges
cloud metadata endpoints
internal services
```

This is especially important if your server ever performs outbound HTTP requests based on user input.

---

Apply rate limits to:

### Authentication

### QR creation

Prevent automated abuse.

### Dynamic redirects

Protect infrastructure from abuse.

### Analytics endpoints

Prevent scraping.

# 77. Acceptance Criteria

## Static QR

A static QR feature is complete when:

* User can enter valid text/URL.
* QR generates successfully.
* Preview is accurate.
* User can customize supported design parameters.
* QR remains scannable under supported configurations.
* PNG downloads successfully.
* SVG downloads successfully.
* Generated QR contains exactly the supplied content.
* No server redirect is required.

---

# 78. Dynamic QR Acceptance Criteria

Dynamic QR is complete when:

* User can create a dynamic QR.
* System generates a unique slug.
* QR contains the platform redirect URL.
* Scanning redirects to the configured destination.
* Scan event is recorded.
* User can edit destination.
* Existing printed QR continues to work after editing.
* Scan counts update.
* Analytics can be filtered by date.
* Device information is displayed where available.
* Approximate geography is displayed where available.
* Activity history records edits.
* Destination versions are retained.
* User can restore an earlier destination version.
* Pausing disables normal redirect behavior.
* Analytics failure does not prevent redirect.
* Malicious/invalid schemes cannot be stored.
