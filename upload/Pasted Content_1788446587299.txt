# QR Platform — Design Specification

Version: 1.0
Status: Implementation Ready

---

# 1. Product

A focused QR platform with exactly two core product features:

1. Static QR
2. Dynamic QR

The product should feel like a tactile editorial design studio rather than a generic SaaS dashboard.

Core product promise:

> Static QR — Encode once.
>
> Dynamic QR — Change anytime. Measure every scan.

The application must prioritize:

- Simplicity
- Scan reliability
- Beautiful QR output
- Fast creation
- Dynamic destination editing
- Useful scan analytics
- Version history
- Security
- Responsive behavior

Do NOT expand the product into a large QR marketplace or marketing automation platform.

---

# 2. Design Direction

The frontend visual language is inspired by the supplied ThreeUI
`MengToSketchbookLandingPage` implementation.

The reference provides:

- Tactile sketchbook atmosphere
- Editorial typography
- Botanical/paper visual texture
- Illustrated surfaces
- Layered compositions
- Page-turn interactions
- Subtle motion
- Hand-crafted visual character
- Strong editorial hierarchy
- Responsive interactions

However:

IMPORTANT:

Do not copy the Singapore portfolio's content, text, information
architecture, or portfolio semantics.

Use the supplied implementation as the exact visual/interaction
foundation where applicable and transform the experience into a QR
creation and analytics product.

The result should feel like:

> An editorial QR design studio.

Not:

> A generic admin dashboard.

# 5. Static QR Definition

Static QR encodes the supplied content directly into the QR.

Example:

```text
User input
    ↓
https://example.com
    ↓
QR encoding
    ↓
Static QR
```

The QR does not require a platform redirect.

The encoded content cannot be changed after generation.

Static QR should be usable with:

* URLs
* Plain text
* Other valid QR-compatible text content

Do not build separate QR-type wizards for V1.

---

# 6. Dynamic QR Definition

Dynamic QR contains a platform-controlled redirect URL.

Example:

```text
QR
 ↓
qr.yourdomain.com/a8K29
 ↓
Redirect service
 ↓
Analytics event
 ↓
Current destination
 ↓
User destination
```

The destination can be changed without changing the printed QR.

Dynamic QR requires an authenticated account.

# 35. QR Scannability

Scannability takes priority over aesthetics.

The system must:

* Use valid QR encoding
* Use appropriate error correction
* Maintain quiet zone
* Validate contrast
* Warn about excessive logo size
* Prevent invalid configurations when necessary

---

# 36. Security

Dynamic redirects are public infrastructure.

Requirements:

* HTTPS
* Authentication
* Authorization
* Rate limiting
* Secure sessions
* Input validation
* URL scheme validation
* Abuse detection
* QR slug unpredictability
* Audit logs
* Error isolation

Reject unsafe schemes such as:

```text
javascript:
data:
file:
```

Only supported web destinations should be accepted for dynamic URLs.

---

# 37. SSRF Protection

If the platform performs URL verification, preview generation,
metadata fetching, or reputation checking:

Never blindly request user-provided URLs.

Block:

* localhost
* loopback addresses
* private IP ranges
* internal services
* cloud metadata endpoints
* other restricted network destinations

---

# 38. Abuse Prevention

The redirect infrastructure must protect against:

* Phishing
* Malware
* Spam
* Redirect abuse
* Automated QR creation
* Slug enumeration
* Credential attacks
* Analytics scraping

Provide:

```text
Report QR
```

for public dynamic QR URLs.

# 39. Redirect Architecture

The redirect path is mission critical.

```text
USER SCANS QR
      │
      ▼
qr.yourdomain.com/a8K29
      │
      ▼
Redirect Service
      │
      ├──────► Queue / Analytics Event
      │
      ▼
Resolve Current Destination
      │
      ▼
HTTP Redirect
      │
      ▼
Destination
```

Analytics processing must not unnecessarily block the redirect.

If analytics is temporarily unavailable:

```text
SCAN
 ↓
Analytics failure
 ↓
REDIRECT STILL WORKS
```

This is a hard requirement.

# 45. Versioning Rule

Never destroy historical destination records.

Bad:

```text
destination = new_url
```

without history.

Correct:

```text
V1 → old URL
V2 → new URL
V3 → another URL
```

Current destination points to V3.

Restoring V1 creates:

```text
V4 → V1 destination
```

This preserves the audit trail.

# 48. IMPORTANT: Exact Source Rule

DO NOT:

* Recreate the component from the screenshot.
* Recreate the component from the description.
* Approximate the animations.
* Replace the authored implementation with a custom interpretation.
* Replace the shaders with CSS approximations.
* Replace the assets with generated substitutes.
* Use screenshots as backgrounds.
* Embed the ThreeUI documentation page.
* iframe the reference website.

FIRST:

1. Fetch the canonical HTML.
2. Fetch the complete registered source bundle.
3. Read the complete source.
4. Verify the required files.
5. Copy/adapt only where required for integration.
6. Preserve authored structure, styling, shaders, motion, dependencies,
   responsive behavior and asset paths.
7. Verify source hashes where available.
8. Copy binary assets byte-for-byte.
9. Verify binary hashes.

IF THE COMPLETE CANONICAL SOURCE CANNOT BE RETRIEVED:

STOP.

Do not approximate the component.

Report that the exact source could not be retrieved.

STATIC QR

Static QR must encode the user's supplied content directly.

Accept:

* URLs
* Plain text
* Other valid QR-compatible text

Static QR has:

* Content input
* Live preview
* QR design controls
* Validation
* PNG download
* SVG download

Static QR cannot be edited after generation.

---

DYNAMIC QR

Dynamic QR must encode a platform-controlled redirect URL.

Example:

qr.yourdomain.com/a8K29

The QR identifier must remain stable.

The current destination must be stored separately.

Example:

QR:

qr.yourdomain.com/a8K29

Version 1:

[https://example.com/offer](https://example.com/offer)

Version 2:

[https://example.com/summer-sale](https://example.com/summer-sale)

The physical QR must continue working after the destination changes.

Dynamic QR requires authentication.

---

DYNAMIC REDIRECT

When the QR is scanned:

1. Resolve QR slug.
2. Validate QR state.
3. Capture a scan event.
4. Resolve current destination.
5. Redirect immediately.

Analytics must not unnecessarily block redirect behavior.

If analytics infrastructure fails, the redirect must still work.

Dynamic redirect performance target:

p95 application processing under 150ms.
